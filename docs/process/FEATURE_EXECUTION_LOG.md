# Feature Execution Log

**Purpose:** Not a record of feature content — a record of how the documentation *process* behaved while producing it, so the Architecture Toolkit and Product Toolkit prompts/workflows can be improved over time.

**What to log:** stage transitions, agents invoked, review iteration counts and why extra rounds were needed, repeated failure patterns (missing evidence, circular reasoning, bad citations, source-verification gaps), Full vs. Delta Review calls, low-value-for-effort spots, and concrete ideas for improving prompts/plugins/workflow/review policy.

**What not to log:** routine steps that went as expected, feature content/requirements themselves (those live in the PRD/ADR/Discovery docs), narration of every tool call.

**Format:** one short dated/staged entry per noteworthy event; a retrospective section at the end of each feature.

**Retrospective — Feature 9 (User Profile & Settings), PRD stage only (Discovery/ADR/C4 stages not yet run):**

- **What consumed the most effort:** Review iteration, overwhelmingly. Four review rounds (2 Full + escalation-triggered Full + 2 Delta) against one PRD, each an independent subagent doing 20-30 tool calls and returning 45-125k tokens of findings. The PRD itself is ~470 lines; the review transcripts across all rounds likely exceeded 10x that in raw token volume. This is a full order of magnitude more expensive than any prior feature in this backlog (Features 1-8 mostly closed in 2-4 rounds total, not 4 rounds on the PRD stage alone before Discovery/ADR even start).
- **Why so many iterations were needed — three distinct, stacking failure classes, each real:** (1) Round 1: claims made about files cited but never opened (the frontend stub). (2) Round 2: claims verified against *one* file when a second file changed the answer (Prisma column nullability, a second sibling implementation, a second registration endpoint). (3) Round 3: claims that should have been cross-checked against the ADR corpus — specifically ADRs' Risks/"does not resolve" sections, not just their Decision sections — were instead treated as newly-discovered by this PRD. Each class is a legitimate process gap, not noise, but three of them compounding sequentially on one document is what made this expensive.
- **Process improvements validated this feature:**
  - The round-1→round-2 pattern (verify one file, miss a second) suggests prd-engine's evidence-gathering step needs an explicit instruction: for any "path A and path B agree/disagree" claim, grep for *all* call sites of the operation, not just the first one found.
  - The round-3 finding is the highest-value one to carry forward: **before filing an Open Question or Failure Condition as "current behavior undefined" or "no settled answer," sweep `docs/architecture/adr/` and `docs/architecture/findings/` — specifically their Risks/Consequences/"does not resolve" sections, not just Decision sections.** This should probably become a standing step in prd-engine's Mode-B evidence-gathering for any feature built after the first several ADRs exist (i.e. not relevant to Features 1-3, highly relevant from here on since the ADR corpus is now 12 documents deep).
- **New improvements to consider before the next feature:**
  - **Cap review rounds up front.** Commit to at most one Full Review + one Delta Review per PRD by default; escalate to a second Full Review only on the reviewer's explicit judgment call (as contract already allows) but treat that as an exception requiring a deliberate stop-and-check with the user, not an automatic continuation. This feature burned through that exception path once (round 2→3) reasonably, but the pattern risks silently repeating on every future feature now that the ADR corpus is large enough to keep surfacing round-3-style gaps.
  - **Consider a lighter-weight review mode for Mode-B (reverse-engineered) PRDs specifically.** Full Review's citation-by-citation verification is expensive and, on this feature, kept finding real things — but the marginal finding value visibly dropped each round (round 1: feature-defining; round 4: wording precision). A cheaper first-pass reviewer (or a self-review checklist run before spawning the subagent) might catch rounds-1-and-2-style gaps at a fraction of the cost, reserving the full subagent review for a single confirming pass.
  - **Track cumulative review cost per feature going forward** (rough tool-call/token count across all review rounds) so the next several features can be compared against this one — if Feature 9's 4-round pattern is a one-off (unusually stub-heavy, unusually deep ADR cross-references) vs. the new normal now that the ADR corpus is large, only comparison across features will show which.
- **Should the workflow change before documenting the next feature (Feature 10 or 11)?** Yes, narrowly: apply the round-cap discipline above before starting Feature 10. Do not change the Discovery/ADR/Review pipeline structure itself — the failures caught were real and worth catching, just at a cost that needs a ceiling. This feature has not yet proceeded past the PRD stage (no `product-reviewer` sign-off issue remains, but Architecture Discovery/ADR/C4 have not started) — recommend pausing here for explicit user go-ahead before continuing to Architecture Discovery, rather than auto-continuing the pipeline.
